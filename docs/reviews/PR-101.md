## Codex assessment summaries

**Crash-consistency ordering**: journal-first, event-log-second is correct. Phantom event without durable journal state is the larger safety risk (loses restart attribution); EventLog.append's residual failure modes are less dangerous than missing journal commits.

**client_order_id ↔ venue order_id**: using Alpaca's response `client_order_id` for both registration and event emission is correct. Stream attribution also uses the venue-returned id, so journal-side key normalization (if Alpaca ever transforms our submitted id) stays consistent across both sides. The full 64-char idempotency key is still stored for replay disambiguation.

**Resolver race**: theoretical only. `register_submission` commits before `BROKER_LIVE_SUBMITTED`; fills cannot legitimately precede accepted submission. Same SQLite file + committed writes give immediate visibility.

**Test coverage**: five tests cover the main wire-in paths. Useful future tests: duplicate `client_order_id` after venue acceptance, journal write failures on fill/cancel paths, EventLog.append failure after successful journal write, exact field persistence.

## Verdict

**APPROVE_WITH_NITS** — the journal-first ordering and venue-view `client_order_id` choice are correct for durability and restart attribution. Remaining risks are edge-case failure semantics worth tracking before live operation but not blockers for this wire-in PR.
