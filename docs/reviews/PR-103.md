## Codex audit notes

**SELECT-before-INSERT under lock**: acceptable for the single-process live-journal contract. Both broker submission writes and stream consumer writes share the same `LiveBrokerJournal` instance, and `threading.Lock` serializes the two SQL statements within one process. A v1→v2 schema migration solely to add `UNIQUE(client_order_id)` is not required. **Caveat**: this is not multi-process safe. If CAQRS later supports multi-process journal writers, add the constraint then.

**Asymmetry with fill-side**: justified. Fills have venue-supplied `execution_id`, so `(client_order_id, fill_id)` is the natural durable key and `sqlite3.IntegrityError` is the clean source of truth. Cancels/rejections have no `cancel_id` analog in Alpaca trade updates; the business invariant is one terminal cancel-like outcome per `client_order_id`. Guarded lookup keeps migration surface smaller while making `consume()` API-level symmetric (journal returns False → emission skipped).

**First-reason-wins on duplicate**: correct semantic for retransmission dedup. If two deliveries disagree on reason, the stream is no longer a pure retransmission and silently replacing the original would destabilize audit trails. A future diagnostic could log reason conflicts; not required here.

**Backward compatibility**: preserved. Pre-existing callers (`test_record_cancel_with_reason`, `test_record_cancel_with_null_reason`) discard the new bool return and continue to pass.

**REJECTED ↔ CANCELED routing**: both go through `record_cancel`; duplicate `rejected` deliveries collapse identically to duplicate `canceled` deliveries. Symmetric per the terminal-event dedup model.

## Verdict

**APPROVE** — closes the PR #102 cancel-side duplicate-emission gap without introducing a schema migration. Lock-based implementation is coherent with the single-process live-journal contract.
