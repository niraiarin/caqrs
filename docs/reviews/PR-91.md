## Algorithm review

- **`make_entity_resolver._resolve`**: walks `IdentifierKind` in declaration order (`JQUANTS_CODE → SEC_CODE → YFINANCE_TICKER → EDINET_CODE → JCN → LEI → POLYMARKET_TOKEN`). First-match wins. The first-match rule is correct given ENT-A3 (one (kind, value) maps to at most one issuer); if two kinds happen to match the same input string, both point to issuers the store has explicitly distinguished, and the declared-first match is a documented footgun-of-convenience. The docstring covers this.
- **`CycleRunner.run()` hook ordering**: the resolver call happens after `cycle_started_event` and the OBSERVING transition, but **before** `_call_agent(observer)`. T-RES-A4 verifies this implicitly (the failing-Observer stub means resolver events must precede the agent-failed event), but the test does not assert ordering directly. A strengthening could pin event-list-position; current coverage is sufficient for the minimal slice contract.
- **Read-only contract**: the resolver receives `observer_input` by reference but only reads `.universe`. T-RES-A3 verifies bytewise identity post-call. The dataclass `IdentifierResolution` is `frozen=True, slots=True` so consumers cannot mutate it after the fact.
- **Sort stability**: the resolver returns resolutions in input order (preserves `observer_input.universe` order). T-RES-A1 implicitly verifies this by indexing via `by_ticker = {r.input_ticker: r for r in resolutions}`. ✓

## Findings

| Severity | Description | Disposition |
|---|---|---|
| minor | The hook ordering "resolver fires after cycle_started but before AGENT_INVOKED(observer)" is asserted via the failing-Observer fixture but not by direct timestamp / event-index inspection. A future tightening could add an explicit assertion that `resolved_events[-1].timestamp <= invoked_events[0].timestamp` or `event_log.events.index(resolved) < event_log.events.index(invoked)`. Not blocking; the failing-Observer construction adequately demonstrates the precedence. | accepted |
| minor | The default IdentifierKind iteration order (declaration order in `caqrs.entities.types`) becomes load-bearing for the "first match wins" rule. If a future contributor reorders the enum, the resolver's prioritisation silently changes. The docstring documents this; consider promoting to a comment near the enum declaration too. | accepted (documented in resolver docstring) |
| minor | `make_entity_resolver` accepts `EntityStore` as a Protocol; any in-memory or DuckDB backend works. There is no concurrency guard if the same store instance is consulted from two cycles in parallel. The InMemoryEntityStore is single-thread-friendly per its docstring; DuckDB is also single-connection-by-default. CycleRunner serialises cycles through CycleQueue, so concurrent resolver calls are not a real risk today. | accepted (out of scope) |
| minor | The Phase E4 slice does not yet wire the resolver into `CycleStore` persistence — the `IDENTIFIER_RESOLVED` events live in the in-memory `EventLog` and persist only when `EventLog(persist_to=...)` is configured. NFR-OBS-2 (lossless JSONL persistence) covers this for any event kind, but a future audit may want explicit assertions that resolution records survive a cycle restart. Phase E4 ships the runtime hook; persistence is implicit. | accepted (covered by NFR-OBS-2 generic round-trip test) |
| minor | The `T-RES-A5` regression guard ("no resolver → no events") is not xfailed; the docstring explains why (it passes pre- and post-impl, so xfailing it would produce a false `xpassed` failure). This is a deliberate departure from ADR-0006's "every new test xfails in step 1" — bounded by the docstring annotation. The verifier accepts the deviation; future ADR-0006 amendments could codify the regression-guard exemption. | accepted (deliberate; documented) |
| nitpick | The `# noqa: PLR0911, PLR0912` suppression on `CycleRunner.run()` now spans two ruff rules. The branch count crossed the threshold because of the new resolver-hook conditional. Could be refactored into a `_run_entity_resolver` helper to drop one branch, but the inline form is more readable for a single conditional. | accepted (inline form preferred) |
